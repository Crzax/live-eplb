# Stage 1 调试记录

三个真实踩过的坑。按暴露难度排序，第三个最隐蔽。

---

## Bug 1：贪心正反馈 —— 均衡反而变差

### 原始规格怎么写的

TODO 里的原文：

> 按贪心法则 $\arg\max_e (w_e / c_e)$ 选出全局最热的逻辑专家进行跨卡复制，
> 并优先放入当前总负载最低的 GPU 冗余槽中。

拆成两步：
1. **选谁复制**：每副本负载 `w_e/c_e` 最大的专家
2. **放到哪**：当前总负载最低的卡

直觉上很合理，我照着实现了第一版。

### 症状

均匀负载（所有专家 `w=1`）下的实测结果：

```
per-rank load: [20, 32, 34, 34, 34, 34, 34, 34]
max/mean = 1.062     (什么都不做的 Static EP = 1.000)
replicas added: 32   (32 个冗余槽全填满)
```

**做了 32 次跨卡复制，结果比什么都不做更差。**

### 根因：两步之间存在正反馈

均匀负载下，初始每张卡负载都是 32，完全平衡。第一轮：

- 所有专家 `w/c` 都是 1.0，`argmax` 取到最小下标的专家 0
- 卡负载全相同，`min` 取到卡 0
- 专家 0 的副本放到卡 0？不行——卡 0 已经持有专家 0（它是 base 专家）
- 于是放到卡 1

关键在于：**专家 0 复制后，卡 0 的负载从 32 降到 31.5**（它持有的专家 0 从 1.0 变成 0.5）。

于是卡 0 成了"最空的卡"。下一轮：

- 选中专家 1（`w/c = 1.0`，仅次于已被复制的专家 0）
- 最空的卡是卡 0
- 专家 1 也在卡 0 上 → 放到别处

但再下一轮，被复制的专家越来越多地**集中在卡 0 的 base 区**，卡 0 持续变轻：

```
卡0 持有 e0~e31，其中被复制过的专家负载减半
→ 卡0 越来越轻 → 越来越容易成为"最空"
→ 但它持有的专家又都已经在它上面了，副本只能去别的卡
→ 别的卡越来越重
```

最终形成 `[20, 32, 34 × 6]` 这个分布：卡 0 独自享受了所有减负的好处，其他卡承担了所有副本的新增负载。

### 更本质的问题

两步贪心的**选择依据和优化目标脱节**：

| | 依据 | 目标 |
|---|---|---|
| 选专家 | `argmax(w_e/c_e)` | — |
| 选卡 | `argmin(load_r)` | — |
| 真正想要的 | — | 最小化 `max(load)` |

`argmax(w/c)` 衡量的是"这个专家的单副本有多重"，但**重不代表复制它有收益**。均匀负载下所有专家一样重，复制谁都没用——可这个判据不会告诉你"没用"，它总能选出一个最大值。

同理 `argmin(load)` 只看接收方，完全不考虑"这次复制让全局峰值变成多少"。

### 修复：直接按目标函数决策

把两步合成一步，**枚举所有 `(专家, 卡)` 组合，算出每种选择下的全局峰值，取最小**：

```python
peak = np.maximum(after_max[:, None], after + add[:, None])   # [E, R]
peak[holds.T] = np.inf
e, r = divmod(int(np.argmin(peak)), num_ranks)
if not np.isfinite(peak[e, r]) or peak[e, r] >= cur_max - 1e-9:
    break
```

最后那个 `break` 是关键：**如果最好的方案都不能让峰值下降，就停手，剩下的冗余槽宁可空着。**

均匀负载下第一轮就触发 break，产生 0 次复制 —— 这才是正确行为，因为复制在数学上就不可能带来收益。

### 验证

`tests/test_planner.py::test_uniform_weight_no_replica`

```python
w = torch.ones(3, E)
phy2log, log2phy, logcnt, tasks = plan_incremental_redundant(w)
assert tasks == []                      # 不产生任何搬运
assert (logcnt == 1).all()              # 每个专家都只有 1 份
for r in range(R):
    assert (phy2log[:, r*SPR+EPR:(r+1)*SPR] == -1).all()   # 冗余槽保持空
l = rank_load(phy2log, w)
assert torch.allclose(l, torch.full_like(l, l[0, 0]))      # 完全均衡
```

### 教训

**"看起来合理的启发式"和"按目标函数直接优化"之间可能有鸿沟。**

两步贪心的问题不是不够聪明，而是它优化的根本不是我们要的东西。当候选空间足够小时（这里只有 256×8 = 2048），直接枚举 + 按真实目标评分，比设计精巧的代理指标更可靠也更好解释。

## Bug 2：`dst_slot` 用了全局槽号

`_diff_tasks` 返回的 `dst_slot` 一开始写成全局槽号（0~287），但 Stage 3 的
`cudaMemcpyPeerAsync` 需要的是**卡内槽位号**（32~35）。

被 `test_copy_tasks_are_valid` 的 `assert EPR <= dst_slot < SPR` 抓到。

修复：`tasks.append((l, e // epr, e % epr, r, epr + i, e))` —— 用 `epr + i` 而非 `r * spr + epr + i`。

这个 bug 很浅，但说明**跨 Stage 的接口约定要在测试里钉死**，否则等到 Stage 3 跑起来才发现，
排查成本会高得多。

## Bug 3：`peak` 只看目标卡 —— 最隐蔽的一个

### 错误实现

中间有一版，我算 `peak` 时只取了**接收方那张卡**的新负载：

```python
buggy_peak = after + add[:, None]      # [E, R]  只有接收方的值
buggy_peak[holds.T] = np.inf
e, r = divmod(int(np.argmin(buggy_peak)), num_ranks)
```

少了外层的 `np.maximum(after_max[:, None], ...)`。

### 为什么难发现

它**不会报错，不会越界，还能正常产出结果**，只是结果是错的。

用一个小例子（2 卡 6 专家，`w = [10, 6, 2, 1, 1, 0]`）对比：

```
load = [18, 2]      cur_max = 18

错误版 buggy_peak:            正确版 peak:
 [[ inf,  7.0]                 [[ inf, 13.0]
  [ inf,  5.0]                  [ inf, 15.0]
  [ inf,  3.0]   ← argmin       [ inf, 17.0]
  [18.5,  inf]                  [18.5,  inf]
  [18.5,  inf]                  [18.0,  inf]   ← argmin
  [18.0,  inf]]                 [18.0, 18.0]]
```

错误版选中 `(e=2, r=1)`：复制**专家 2**（`w=2`，第三热）。
正确版选中 `(e=0, r=1)`：复制**专家 0**（`w=10`，最热）。

### 根因

`argmin` 找的是"哪个方案的 peak 最小"。

错误版里 `buggy_peak[e, r]` 的含义是"**接收方卡 r 接收后的负载**"。要让这个值最小，
最优策略是**复制一个尽量轻的专家**——因为轻专家的 `add` 小，接收方涨得少。

于是算法系统性地偏好冷门专家，而冷门专家对降低峰值毫无帮助。
真正的瓶颈卡（卡 0，负载 18）根本没被改善。

正确版的 `peak[e, r]` 是**全局最大卡负载**，包含了瓶颈卡。复制热门专家才能把瓶颈卡拉下来，
所以 `argmin` 会正确地选中专家 0。

### 现场症状

当时在 `tutorials/01_eplb_diff.py` 看到的是：

```
LiveEPLB       plan@t0           2.369       14584    ...
```

Max/Mean 和 Static EP **一模一样，一个数字都没动**。槽位确实被填了，但填的全是冷门专家，
对均衡毫无贡献。

### 为什么测试没抓到

那一版 `tests/test_planner.py` 已经有 11 个测试全过了，因为它们检查的都是**结构性质**：

- base 槽没动 ✓
- `phy2log` / `log2phy` 互逆 ✓
- 同卡无重复专家 ✓
- `copy_tasks` 字段合法 ✓

**所有结构都对，只有"有没有用"是错的。**

是跑对比脚本时看到 `Max/Mean` 一动不动，才意识到不对。

### 修复与补测

修复就是补上全局 max：

```python
after_max = after.max(axis=1)                                 # [E]
peak = np.maximum(after_max[:, None], after + add[:, None])   # [E, R]
```

补的测试 `test_improves_imbalance`：

```python
r0 = (l0.max(-1).values / l0.mean(-1)).mean()     # 基线
r1 = (l1.max(-1).values / l1.mean(-1)).mean()     # 规划后
assert r1 < r0 * 0.75                              # 必须显著改善
assert torch.allclose(l1.sum(-1), l0.sum(-1), rtol=1e-5)   # 总负载守恒
```

两条断言各有分工：
- 第一条防"没效果"（就是这个 bug）
- 第二条防"假效果"——如果 `rank_load` 的 `w/c` 分摊算错了，均衡度会虚假地变好，
  但总负载会偏离

### 教训

**测试全过 ≠ 正确。**

结构性测试（shape 对不对、映射互不互逆、字段合不合法）只能保证"代码没崩"，
保证不了"算法有用"。必须有一条测试直接检查**端到端的效果指标**，
而且要和基线对比，不能只看绝对值。

补充一点：这类 bug 靠读代码很难发现，因为 `after + add` 这个表达式本身看起来就是对的
（它确实算出了接收方的新负载）。真正有效的手段是**打印中间矩阵，用小规模数据手算核对**。
上面那个 2 卡 6 专家的例子就是我后来用来定位的。

## 三个 bug 的共性

| | 会不会报错 | 结构测试能否发现 | 靠什么发现的 |
|---|---|---|---|
| Bug 1 正反馈 | 否 | 否 | 专门的退化场景测试（均匀负载） |
| Bug 2 槽号 | 会（越界） | **能** | 接口约定断言 |
| Bug 3 peak | 否 | 否 | 端到端指标异常 |

两个最严重的（1 和 3）都是"安静地给出错误答案"，而且都是**优化目标没对齐**导致的：
Bug 1 用代理指标替代目标函数，Bug 3 算错了目标函数本身。

所以 Stage 2 之后的测试策略定为：**每个 Stage 至少有一条测试直接断言"这个优化真的生效了"，
而不只是"没有崩"。** 比如 Stage 2 要断言换权后的输出命中手算期望值，
而不是只断言 `replay()` 没抛异常。
