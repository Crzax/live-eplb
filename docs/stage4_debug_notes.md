# Stage 4 调试记录

十六个 bug。其中**只有两个会报错**，其余十四个都是"跑得通、数字也不离谱、但结论是错的"。
尖刺排查尤其典型：连续四轮以为修好了，每轮都冒出一个新的、更隐蔽的瓶颈；而最后几个里
S4-11 是把层数从 1 扩到 40 才从噪声里浮出来的，S4-12 完全没有任何指标报警——它是被
"这个判据凭什么"这个问题问出来的，S4-16 则是**单方面偏向我自己的测量偏差**，修完之后
文档里关于收敛过程的整节结论都变差了。

有两类错误在这一阶段各犯了两次：**一个数字同时承担两个角色**（S4-12 的层平均既当代价又当
门控、S4-16 的 `phy2log` 既当规划输入又当现状报告），以及**CPU 侧阻塞被 replay 完美掩盖**
（S4-11、S4-15）。

## S4-1：规划跑在关键路径上

### 症状

第一版控制器把 `plan_incremental_redundant` 直接写在 `on_step()` 里，TPOT 曲线在每个
规划步出现 33.7 ms 的尖刺。

### 根因

规划是纯 CPU 的贪心，单层 4.9 ms、40 层 188 ms（Stage 1 实测），而一个 decode step
是 6.4 ms。**把一个比 step 长一到两个数量级的东西放进 step 里，必然是尖刺。**

### 修复

丢到 worker 线程，主循环只查完成状态。这是整个 Stage 4 的核心设计，也是
SwiftBalancer 把 EPLB 算法挪进独立 worker 的同一个理由。

---

## S4-2：`enable_peer_access` 失败时留下粘滞错误

### 症状

8 卡跑 benchmark，在一个和 P2P 毫无关系的 `dist.barrier()` 上报 CUDA 错误。

### 根因

```cpp
cudaError_t e = cudaDeviceEnablePeerAccess(peer_rank, 0);
if (e != cudaSuccess && e != cudaErrorPeerAccessAlreadyEnabled) {
  cudaGetLastError();     // 只在"真失败"的分支里清
  return false;
}
```

`cudaErrorPeerAccessAlreadyEnabled` 走的是另一条路径，**错误码没被取走**。CUDA 的错误是
粘滞的：下一次任意 CUDA 调用都会把这个陈年错误报出来，于是它落在了后面某个无辜的
`dist.barrier()` 上。

### 修复

任何非成功返回都先 `cudaGetLastError()` 清掉，再判断是不是"已启用"这种良性情况。

### 教训

**错误码不消费就会漂移到别处。** 报错的位置和出错的位置无关，是这类 bug 最贵的地方——
我一开始在排查 NCCL。

## S4-3：全局槽号与卡内槽号混用

规划器输出的 `log2phy` 用全局槽号（0~287），而每张卡的 `W_pool` 只有 36 个槽、
`cudaMemcpyPeerAsync` 要的是卡内槽号（0~35）。直接把全局号写进分片的表里，索引越界。

这和 Stage 1 的 Bug 2 是同一类（当时是 `dst_slot`），**同一个概念在两套编号体系里穿行，
第二次还是栽了**。现在转换集中在 `rank_local_tables()` 一个函数里，控制器和 benchmark
的 stw 基线共用它，不再有第二份实现。

## S4-4：规划线程里 113.9 ms 的 Python 循环

### 症状

修好 S4-1 之后尖刺没消失，只是从"规划步 33.7 ms"变成"规划期间的若干步 10~22 ms"。

### 定位

把规划线程里的两段分别计时：

```
plan_incremental_redundant   4.9 ms
_host_tables 的 Python 循环  113.9 ms      ← 23 倍于规划本身
```

那个循环是逐专家 `for e in range(256)`，里面还有 `int(s)` 这种逐元素标量取值。

### 根因

**它在后台线程里，但它持有 GIL。** 后台线程只能让出 I/O 和大块 numpy 的 GIL；
纯 Python 的循环会和主线程抢 GIL，主线程每次要等一个切换间隔（默认 5 ms）。
于是尖刺从"一步 33 ms"摊成了"连续若干步各慢 10 ms"——**看起来好转了，其实只是变形了**。

### 修复

向量化：

```python
keep   = (src >= 0) & (src // spr == rank)
local  = torch.where(keep, src % spr, -1)
packed = local.gather(1, torch.argsort((~keep).int(), dim=1, stable=True))
```

113.9 ms → **0.083 ms，1370 倍**。

### 教训

"扔到后台线程"不等于"不影响主线程"。**Python 的后台线程只隐藏阻塞，不隐藏计算。**
判断标准很简单：这段代码是不是在持 GIL 的情况下跑了很久。

## S4-5：1 KB 的统计 all-reduce 走 NCCL，尖刺来自 GPU

### 症状

向量化之后尖刺**变得更大**（worst 从 31 ms 涨到 50 ms），而且随机出现在 `planning`、
`cooldown`、`idle` 各种步上。

### 定位

给控制器每个阶段单独计时，结果是**所有阶段加起来都不到 0.3 ms，但那一步的
`torch.cuda.synchronize()` 等了 37 ms**。既然 CPU 侧没花时间，问题就在 GPU 上。

当时 GPU 上唯一多出来的东西是统计的 `dist.all_reduce(stats_gpu, async_op=True)`。

### 根因

两层：

1. **NCCL 的 kernel 在 GPU 上自旋等 peer。** `async_op=True` 只是不阻塞 CPU，kernel
   照样占着 SM 空转，直到最慢的 rank 入场。
2. **集合通信会把 rank 间的时间偏斜暴露出来。** 八个进程各自的 Python 调度抖动原本互不
   影响，一旦有集合通信，**最慢的那个决定所有人**。

1 KB 的数据量在这里完全不是重点——代价不在带宽，在同步语义。

### 修复

统计改走 **CPU（gloo）组**，并且放进一个常驻的 reduce 线程：

```python
def _reduce_stats(self):          # 主循环：只做快照 + 信号量
    self.stats_q.append(self.ema.cpu())
    self.stats_tick.release()

def _stats_loop(self):            # 后台：按发起顺序逐个 reduce
    while True:
        self.stats_tick.acquire()
        snap = self.stats_q.pop(0)
        dist.all_reduce(snap, group=self.group)
        self.stats = snap
```

另外把触发改成**无条件、固定步长**（`step % check_every == 0`）。原来的写法是
"状态机进 PLANNING 时顺便 reduce"，而各 rank 的状态机可能因为拷贝完成时刻不同而错开，
**一个 rank 进了集合通信、另一个没进，就是死锁**。现在 reduce 和状态机完全解耦。

### 教训

**"异步"只保证不阻塞发起方，不保证不干扰别人。** 和 Stage 3 的 copy engine 是同一种
错误的第二次出现：那次是 copy engine 不占 SM 但占 HBM，这次是 NCCL 不阻塞 CPU 但占 SM。

## S4-6：每次规划新建线程，线程启动落在关键路径上

修完 S4-5 后还剩一个尖刺：step 236，47.33 ms，其中 47.26 ms 在 `on_step()` 内部，
而该步做的事只有 `_start_planning()`：两次 clone + `threading.Thread(...).start()`。

`Thread.start()` 要等新线程真正起来才返回。八个进程、每个进程主线程 + 规划线程，
在一台 CPU 已经被压满的机器上，这个握手可以拖到几十毫秒。

改成**常驻 worker + 信号量**，`_start_planning()` 退化成三行赋值加一次 `release()`。
至此 live 的最差单步从 47.3 ms 降到 7.0 ms，**全程没有任何一步超过 10 ms**。

> 这四轮（S4-1、S4-4、S4-5、S4-6）值得一起看：每修掉一个，下一个瓶颈就暴露出来，
> 而且四个的性质完全不同——关键路径上的计算、持 GIL 的后台计算、GPU 上的集合通信、
> 线程创建本身。**"后台执行"不是一个开关，是一串需要逐个验证的条件。**

## S4-7：覆盖仍在服务的冗余槽

### 症状

写 `test_occupied_slot_is_unlinked_before_overwrite` 时发现的——不是跑出来的，是**先想到
这个场景，再写测试去证实**。

第二次规划会把冗余槽重新分配给别的专家。此时槽里装的是第一次规划的副本，而且**路由表里
指向它**，正在接 token。`cudaMemcpyPeerAsync` 直接往里写，那一刻读到的就是半新半旧的权重。

### 为什么 Stage 2 的论证在这里不成立

Stage 2 说"空槽收不到 token，所以拷贝和推理可以重叠，不需要互斥"。那个结论的前提是
**目标槽是空的**。第一次规划之后，冗余槽不再是空的了。

这正是 xLLM 需要 staging buffer + 两阶段 prepare/activate 的原因。我们之前以为
Pinned-Base 可以免掉这一层，其实只免掉了 base 槽那部分。

### 修复

拷贝之前先提交一张**摘除表**：把即将被覆盖的槽从 `log2phy` 里摘掉（`logcnt` 相应减 1），
其余条目紧凑左移。

```python
keep = (l >= 0) & ~torch.isin(l, slots_about_to_be_overwritten)
```

槽变成不可达之后再拷贝，Stage 2 的论证就重新成立了。代价是这些专家在迁移窗口内少一个
副本——**负载短暂地差一点，但永远不会读到损坏的权重**。

提交摘除表和发起拷贝在同一条流上，且 `pull_batch` 会 `wait_stream(current)`，所以
"摘除表生效"一定排在"开始写槽"之前，不需要额外的同步原语。

### 教训

**前提条件会随着系统演进失效。** Stage 2 的不变量（目标槽永远是空的）在单次迁移下成立，
在连续迁移下不成立。写下不变量的时候要同时写下它依赖什么。

## S4-8：`min_gain` 门控把失效的布局锁死了

### 症状

流量突变后，live 全程只提交 2 次，最后 100 步的 Max/Mean 和 static 几乎一样。

### 根因

`min_gain` 的逻辑是"当前不均衡度和上次规划时相比变化不足 0.05 就不重新规划"，本意是
避免反复付规划的钱。问题出在突变那一刻：

1. step 80 突变，EMA 刚吃进一步新流量，此时的统计是**新旧混合**的
2. 不均衡度越过阈值，触发规划 → 得到一个**对两边都不对**的布局
3. 这个布局没把不均衡度压下去，于是 `|imb - planned_at|` 一直很小
4. **门控认为"没变化，不用重算"，而真相是"变化了但我修错了"**

### 修复

直接删掉 `min_gain` 和 `planned_at`。它存在的理由是"规划很贵"，而规划现在已经完全在
后台（S4-1/4/6），单次 4.9 ms。节流交给 `cooldown_steps`，浪费由
`_absorb_plan()` 里"新计划和当前布局相同就不拷贝"兜底。

### 教训

**用"收益的代理量"做门控，在代理量本身失真时会反向锁死。** 这和 Stage 1 Bug 1
（用 `argmax(w/c)` 代理"复制是否有收益"）是同一类错误：**判据和目标不是一回事。**

## S4-9：测试里的同步断言，把被测的异步行为等没了

### 症状

`test_copying_never_blocks` 在测试套件里稳定失败，单独跑却稳定通过。断言信息是
`acts.count("copying") == 1`——本该有 200 多个 copying 步。

### 根因

测试循环里有这么一行：

```python
if a == "copying":
    assert torch.equal(shard.log2phy, before)   # 验证表没被提前改
```

`torch.equal` 要把结果读回 CPU，**会同步**。于是第一次轮询返回 "copying" 之后，
这个断言把那 200 ms 的拷贝整个等完了，下一次轮询自然就绪 → 直接 commit。

**测试把它要观测的现象消灭了。**

### 修复

循环里只做无同步的 `clone()` 快照，循环结束后统一比较。

### 教训

和 Stage 2 Bug 1（计时测成了入队）是镜像的两面：那次是"没同步，测到的不是执行"，
这次是"多同步了，测到的不是并发"。**凡是涉及异步的测试，都要先问：我这行代码会不会
同步？**

## S4-10：benchmark 每步重洗热点，收益被自己消掉了

### 症状

所有尖刺修完之后，live 的均衡曲线和 static 基本重合：step 150-300 的平均 Max/Mean
是 **live 1.244 对 static 1.235**，live 反而略差。但离线单独跑规划器，同一个流量模型
能把 1.256 压到 1.081。

### 定位

离线算期望负载（不采样）下的不均衡度：**2.232**。而 benchmark 里测出来的 static 只有
1.28。差了这么多，说明两边的"流量"根本不是一回事。

回去看 benchmark 的采样函数：

```python
def zipf_counts(tokens, experts, alpha, shift, gen):
    perm = torch.randperm(experts, generator=gen)      # ← 每步都重新洗
```

**每一步的热点专家都是全新的随机排列。** 均摊下来每个专家一样热，EMA 收敛到均匀分布。

### 后果

这不是"收益变小了"，是**整个实验失去了意义**：
- 测到的 Max/Mean ≈ 1.28 全部是 256 token 的采样噪声，不是结构性倾斜
- 任何放置策略都不可能有收益，因为下一步的热点和这一步无关
- 我差点把"live 和 static 均衡度一样"写成"合成负载下收益有限"的结论

### 修复

热点集合在一个相位内固定，只在突变点整体轮转：

```python
perm = torch.randperm(experts, generator=torch.Generator().manual_seed(0))
probs[(perm + shift) % experts] = p / p.sum()
```

修完之后 static 的 Max/Mean 从 1.28 变成 2.18，live 压到 1.15，图才有东西可看。

### 教训

**负载模型错了，所有性能数字都是在测噪声。** 而且这个错误特别阴——它不会让程序崩，
不会让数字离谱，只会让收益悄悄变成 0，然后你开始怀疑自己的算法。

## S4-11：藏在"后台"里的同步 D2H，被 40 层放大 32 倍才现形

### 症状

单层跑通之后扩到 40 层，live 的最差一步里出现这么一行：

```
live step 15 idle  TPOT 66.39 ms, of which controller CPU 65.91 ms
```

动作是 `idle`——没规划、没拷贝、没提交，什么都没干，但 `on_step()` 内部花了 65.91 ms。

### 根因

`_reduce_stats()` 的第一行：

```python
snap = self.ema.cpu()
```

`ema` 在 GPU 上（`record()` 刻意把它留在 GPU，避免每步 D2H）。`.cpu()` 是**同步**拷贝，
会阻塞调用线程直到当前流排空——而当前流上正排着这一步的 40 层 graph replay。
所以这 65.91 ms 就是"等 GPU 跑完"。

step 15 命中是因为 `check_every = 8`，第 16 步做规约。

### 为什么单层没发现

单层时这个同步是 **2.06 ms**，和单步耗时 1.6 ms 同量级，混在抖动里。我当时在文档里
写的是"p99 的 6.7 ms 全部落在每 8 步一次的统计快照上……这不是额外开销，那一步无论如何
都要等 GPU 跑完"——**这句话是对的，但它掩盖了问题的性质**。

TPOT 确实没有被推高：CPU 的 65.91 ms 和 GPU 的 65 ms 完全重叠，这一步总共 66.39 ms，
只比 static 的最差步高 0.43 ms。**从 TPOT 曲线上永远看不出这个 bug。**

但"从不阻塞"这个声明在 CPU 侧是假的。在这个 benchmark 里 CPU 闲着无所谓，真实引擎里
这段时间本该用来做下一步的采样、detokenize、调度。

### 修复

pinned 环形缓冲 + 异步 D2H + event，让规约线程去等：

```python
buf = self.snap_ring[self.snap_i]
self.snap_i = (self.snap_i + 1) % len(self.snap_ring)
buf.copy_(self.ema, non_blocking=True)
ev = torch.cuda.Event(); ev.record()
self.stats_q.append((buf, ev))
```

```python
# _stats_loop
buf, ev = self.stats_q.pop(0)
ev.synchronize()        # 等在后台线程里
snap = buf.clone()      # 环槽会被复用，先占为己有
self.snap_free.release()
```

效果：控制器 CPU 的最大值 **65.91 → 0.21 ms**，live 的最差一步 66.39 → 66.04 ms
（static 是 65.97）。

### 一个顺手写错又改回来的决定

环满了怎么办？第一版写的是跳过本次规约，注释还写着"每个 rank 都会在同一步跳过，
所以集合通信仍然配对"。

**这句话是错的。** 队列长度是 rank 本地状态，各 rank 的 gloo all-reduce 快慢不同，
完全可能一个 rank 跳过而别人没跳——那就是 S4-5 同一个坑的另一面：**集合通信失配 =
死锁**。改成信号量背压：环满时主线程等，所有 rank 的 all-reduce 次数严格一致。

默认配置（8 步一次 vs 几毫秒的 gloo）下实测从未等过，但这是一条真实的阻塞路径，
已记进局限。

### 教训

**"它没有让指标变差"不等于"它没有问题"。** 这个同步点被两件事同时掩盖：一是它和
GPU 的工作完美重叠，二是单层规模下它只有 2 ms。扩规模把它放大了 32 倍才看见。

更该反省的是：上一版文档里我已经注意到了这 6.7 ms，还给它写了一段解释，然后**把它
归类成"合成负载的产物"放过了**。真正的问题不是 D2H 存在，而是它是同步的。
给一个异常现象找到一个说得通的解释，和这个解释正确，是两件事。

发现它靠的是**离线复算**：同一个规划器、同一个流量模型，离线能做到 1.081，在线做不到，
那差的一定不是算法。**两条独立路径算同一个量，不一致就是信号。**

## S4-12：判据是每层的，动作却是整栈的

### 症状

没有症状。这个 bug 是被**问出来**的：复制专家的收益判据是"某一层的卡间负载是否均衡"，
但决定要不要触发的阈值取的是 40 层的**平均** Max/Mean。

### 根因

两件事混在了一个数字里。

Max/Mean 的层平均**作为代价度量是对的**：每层路由同样多的 token，所以每层的 mean
相同，一个 step 的耗时正比于逐层最慢卡之和，于是层平均恰好等于"比完美均衡慢多少"。
实测验证：构造 k 层倾斜、其余均衡，k=12 时层平均 1.351、实测单步代价 +35.1%。

但**作为门控是错的**：冗余槽预算是逐层独立的，40 层就是 40 个互不相干的子问题。
一层极度倾斜被 39 层正常的稀释掉之后，那一层不会因为"全栈平均还行"而变得不值得修。
量化这个盲区：11 层倾斜时单步代价已经 +32%，其中 18% 可以靠复制收回，而层平均只有
1.32，**阈值 1.35 不触发**。

更要紧的是：我自己的 benchmark 看不见这个盲区。`phase_probs` 给 40 层同一个 α，
只轮转热点集合，于是每层的 Max/Mean 几乎相同，max 恒等于 mean。**盲区是我生成数据的
方式造出来的**，不是测出来没有。

### 走错的一版

第一反应是把门控从 mean 换成 max。GPU 上跑完就否掉了：改成 max 之后永不收敛——
最差那层规划后仍在 1.35 以上，于是每过一次冷却就重新触发。stw 提交 3 → 15 次，
p99 67.1 → 163.9 ms；live 的拷贝步 27 → 72 步，换来 2% 的均衡改善。

**这一版让我的对照实验更好看**（stw 被自己的门控打残），所以必须否掉：那个差距来自
门控设计缺陷，不来自 LiveEPLB 的机制。

### 修复

缺陷不是 max 还是 mean，是**用逐层的判断去驱动整栈的动作**。规划器加 `layers` 参数，
只重排点名的层，其余层原样保留 `prev_phy2log`；门控改成"挑出所有超阈值的层"，
一层都没有才 idle。

顺带补了一个**不回退保护**：在同一份权重上比较新旧布局的峰值卡负载，没有改善就保留旧的。
全量重规划时它拒掉了 164 次纯回退的拷贝——贪心对单层最优，不保证对上一轮的布局单调。

### 教训

**一个数字同时当代价和当判据，是两个角色。** 它在前者上是对的，恰好掩盖了它在后者上
是错的。另外：我的 benchmark 没报警，不是因为系统没问题，而是因为**合成负载让 40 层
长得一模一样**——对照组的多样性也是实验设计的一部分。

## S4-13：分段计时把 replay 的排空算进了拷贝

### 症状

stw 的停机分段里出现两种自相矛盾的组合：`plan 34.0 / copy 32.1` 和
`plan 1.7 / copy 62.8`。plan + copy 恒等于约 64 ms —— 正好是一个 decode step。

### 根因

`pull_batch` 里 `s.wait_stream(torch.cuda.current_stream())`，而本步的 replay 刚入队。
所以计时器一跨过 `pull_batch`，就把**等 replay 跑完**的时间记成了拷贝时间。
规划在 CPU 上先跑，规划越久，剩下要等的 replay 越短，两段此消彼长，和恒定。

于是**文档里"copy 2.8 ms、折合 320 GB/s"这个数字是蒙对的**：它出现在规划最久的那几步，
replay 恰好已经被规划等掉了。

### 修复

分段里加一列 `drain`：`pull_batch` 之前显式 `torch.cuda.synchronize()`，把等 replay
的时间单独记出来。修完的分解是 plan 1.9-37.9 / drain 26.5-62.4 / copy 0.2-3.9 /
recapture 47.0-60.1，plan + drain 仍然恒为一个 step —— 这次是因为**规划藏在 replay
背后，不花额外的钱**。

### 教训

分段计时抓到了 S4-4/5/6，这次它自己是 bug 的来源。**两段之和恒定，就是分界线画错了的
signature**——单看任一段都像合理的波动。

## S4-14：规划器里又是两个 Python 循环

### 症状

把 plan 从 drain 里分出来之后，plan 在 40 层全量规划时是 58.8 ms，远超 Stage 1 对
贪心本体的估计。

### 根因

和 S4-4 同一类，只是换了函数：`log2phy_from_phy2log` 里一个 `for l: for s:` 的双层循环
66.9 ms，`_diff_tasks` 里一个 `for l: for r: for i:` 的三层循环 9.6 ms。两者都是纯索引
搬运，没有任何计算。

这推翻了文档里那句"规划占停机的 60%，而那是 EPLB 本来就要付的钱"——**那 60% 里的大头
是我自己的实现效率，不是 EPLB 的算法代价**。

### 修复

都改成张量操作。`log2phy_from_phy2log` 用稳定 `argsort` 加组起始偏移（第一版写成
`[L, S, E]` 的 `cumsum`，内存太重，又退回来）；`_diff_tasks` 改成在 `[L, R, red]` 上
做掩码 `nonzero()`。

```
log2phy_from_phy2log   66.9 → 0.8 ms   (84x)
plan 全量 40 层        129  → 58.8 ms
plan 热点 2 层         76.5 → 3.5 ms
```

两个函数都用随机差分测试对着原循环验过（300 / 400 组随机输入，逐元素相等）。

### 教训

**同一类 bug 会在同一个项目里出现两次。** S4-4 修的是规划线程里的循环，这次是规划器
内部的循环，隔了一周。修完一个瓶颈之后，剩下的部分从来不会自动变干净。

## S4-15：第一次 launch 的模块加载，被记成一个完整的 decode step

### 症状

控制器 CPU 全程有界（p50 0.05 ms），只有两步例外：step 0 的 64.33 ms 和 step 27 的
65.79 ms。两个数都约等于一个 decode step，而 step 27 是整轮**第一次 commit**。

### 根因

CUDA 的模块加载和 pageable H2D 都要等设备空闲。而 `on_step` 的调用点是
`replay()` 的紧后面，所以**任何一次首启开销都会先等掉一整个 replay**，再加上自己的
十几毫秒。拆出来看：

```
record         首次 14.025 ms，之后 0.053 / 0.012 / 0.010   # EMA 的 pageable H2D + 首启
layer_imbalance 首次  1.872 ms，之后 0.245 / 0.166
commit kernel  首次（step 27）65.79 ms                      # .so 里这个 kernel 的模块加载
```

两个数都没有推高 TPOT（step 0 的 TPOT 是 64.73，p50 64.55），因为它们和自己在等的那个
replay 完全重叠。**这和 S4-11 是同一个形状**：CPU 侧阻塞，TPOT 上看不见。

### 修复

在构造函数里做掉，那时还没有 replay 在飞：一次 no-op commit（把表提交成它自己）、
一次全零 `record`（零不改变 EMA）、一次 `layer_imbalance`。构造函数里本来就已经有
`pin_memory()` 的同类预热和 benchmark 里的规划器预热，这是把同一条规矩补齐。

效果：live 的控制器 CPU 最大值 **65.79 → 0.58 ms**，300 步里再没有超过 1 ms 的步。

### 教训

S4-11 的教训是"重叠≠无代价"，这次是同一条，但触发方式不同：**首启开销不是性能问题，
是一次性的，可是它落在哪一步是由调用顺序决定的**。只要那一步在真实引擎里要用 CPU 去
准备下一个 batch，它就是真实的损失。预热应当是构造期的纪律，而不是等它在某一步冒出来。

## S4-16：均衡曲线给 live 提前记了功

### 症状

看最终的 TPOT 图时注意到：live 的 Max/Mean 在 step 125 附近就掉下来了，而它那一轮的
提交发生在 step 130。**收益出现在动作之前。**

### 根因

`_absorb_plan()` 里一行 `self.phy2log = phy2log`。它在 COPYING **开始**时就把新布局
写进了 `self.phy2log`，而 `layer_imbalance()`（以及 benchmark 的均衡曲线）正是读这个字段。
于是整个 COPYING 窗口——平均 2.9 步，最长十几步——报告的是**还没生效的布局**的均衡度。
`layer_imbalance` 的 docstring 写着"under the placement in force"，那句话是假的。

对照组不受影响：stw 是同步的，`base_phy2log` 和真实切表在同一步发生。所以这是一个
**单方面偏向 live** 的测量偏差。

### 修复

新布局存进 `planned_phy2log`，只在 commit 分支里才赋给 `self.phy2log`。

影响比预想的大：突变后那一段的均衡峰值**从 1.46 变成 2.09**，live 落后 stw 的窗口从
"约 25 步、最大差 0.19"变成"约 45 步、最大差 0.81"。文档里关于收敛过程那一节整段重写了。

### 顺带掉出来的第二个问题

加了 `test_imbalance_reports_the_layout_in_force_while_copying` 之后，另一个老测试
`test_skew_goes_through_every_state_in_order` 挂了：状态序列多了一个开头的 `idle`。

追下去发现构造函数里 `self.stats = self.ema` 是**别名**。测试里 counts 在 CPU，
`record()` 就地改 `ema`，`stats` 跟着一起变，于是门控在第一次统计规约之前就能读到数据；
真机上 counts 在 GPU，`record()` 会把 `ema` 搬到 device 从而**断开别名**，`stats` 保持
全零直到第一次 reduce。

也就是说：**这个测试一直在验证一条真机上不存在的路径**。改成 `.clone()` 之后，测试看到的
序列（多一个等统计的 `idle`）才是真机的序列，断言也相应放宽。

### 教训

**"收益出现在动作之前"是因果倒置，看到就该停下来查。** 它不会让任何断言失败——两个数都
在合理范围内，曲线形状也好看，只是时间轴错位了几步。

另外：一个字段同时被"规划输入"（prev_phy2log）和"现状报告"（imbalance）两个用途读，
就必然有一个时刻是错的。这和 S4-12"一个数字当两个角色"是同一类错误，隔了几个小时又犯一次。

| S4-3 槽号编号体系混用 | 代码 | 异常 | 是 |
| S4-4 持 GIL 的后台循环 | 认知（线程≠并行） | 分段计时 | 否 |

| S4-6 线程创建的代价 | 认知 | 分段计时 | 否 |
| S4-7 覆盖在役槽位 | 不变量失效 | **写测试时主动设想** | 否 |

| S4-11 同步 D2H 藏在后台路径里 | 认知（重叠≠无代价） | **扩规模放大 32 倍** | 否 |

| S4-13 分段把 replay 排空算进拷贝 | 测量方法 | **两段之和恒定** | 否 |
| S4-14 规划器内部的 Python 循环 | 认知（同 S4-4 复发） | 分段计时 | 否 |
| S4-15 首次 launch 的模块加载 | 认知（重叠≠无代价） | 逐步 CPU 计时的离群点 | 否 |
| S4-16 均衡曲线提前记功 | 测量方法（偏向自己） | **收益出现在动作之前** | 否 |

累计到 Stage 4，二十四个 bug 里**会报错的只有四个**（S1-2、S3-1、S4-2、S4-3）。

真正抓到问题的手段，按有效性排序：

1. **分段计时 + 排除法**（S4-4/5/6/14）—— "各阶段加起来 0.3 ms，但这一步花了 37 ms"，
   这种自相矛盾比任何猜测都有用；它的反面是 S4-13，分界线画错时同样会自相矛盾
   （两段之和恒定）
2. **离线复算同一个量**（S4-10）—— 两条独立路径对不上，必有一错
3. **把规模推上去**（S4-11）—— 单层下 2 ms 的东西在 40 层下是 66 ms，
   有些 bug 只在量级变化时才从噪声里浮出来
4. **被追问设计依据**（S4-12）—— 没有任何指标报警，是"这个判据凭什么"这个问题
   把它问出来的
5. **端到端指标异常**（S1-3、S4-8）
6. **主动设想竞态再写测试**（S4-7）—— 单元测试本身抓不到，得先想到
7. **对照实验**（S1-4）
8. **人工 review**（S2-2）
9. 单元测试（S1-2、S3-1、S4-3）—— 只能抓会报错的那类

还有一条贯穿 Stage 2-4 的模式：**"因为 X 所以不会 Y" 这种推理，错了三次**。
copy engine 不占 SM 所以不干扰（错，占 HBM）、异步 all-reduce 不阻塞所以不影响
（错，占 SM 且暴露偏斜）、后台线程不在关键路径所以不影响（错，持 GIL）。
**共享资源总比看上去多一层。**

而 S4-11/S4-13/S4-15 合起来是另一条：**只看 TPOT 看不出 CPU 侧的阻塞**，因为它们
都和自己在等的那个 replay 完美重叠。要查这一类，必须单独计量 CPU 时间。
